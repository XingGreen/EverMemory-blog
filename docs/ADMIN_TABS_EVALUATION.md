# D3 后台内部标签页体系可行性评估

> 排查项，产出结论而非代码。审计时间 2026-11-25。

## 一、现状

后台导航目前是**单页单路由**模型，共 9 个导航项：

```
首页 / 文章管理 / 分类与标签管理 / 网站配置 / 环境变量 / 友链管理 / 会话管理
（另有：文章历史版本、同步工作台，从页面内部进入）
```

路由用 History API 真实路径（`/admin/posts/`、`/admin/env/` 等），
`AdminDashboard.svelte` 里的 `parseRoute()` / `applyRoute()` 负责解析。

`type Page` 共 11 个值（含 `history`、`sync`、`404`）。

## 二、什么是「标签页体系」

指在后台内部同时打开多个页面，用标签栏切换，例如：

```
[首页] [文章: xxx] [环境变量] ×
```

类似浏览器标签，切走再切回时**保留原页面状态**（滚动位置、未保存的输入）。

## 三、可行性分析

### 技术上的三个硬约束

**1. `AdminDashboard.svelte` 是单实例巨石（5663 行）**

页面通过 `{#if}` 条件块切换渲染，不是独立组件树：

```svelte
{#if activePage === "dashboard"} ... {:else if activePage === "posts"} ...
```

要并存多个页面，必须把每个分支改成**保留挂载 + 隐藏切换**，
但 `PostEditor` 一个实例就持有 2400+ 行状态、编辑器 DOM、草稿定时器、
路由锁、beforeunload 监听器 —— 多实例会让这些副作用互相干扰
（例如两个编辑器同时注册 `beforeunload`）。

**2. 路由锁机制与「多开」直接冲突**

现有 `tryLockRoute()` 的语义是：**同一路由同一时间只允许一个标签页**，
不同路由互不影响。它已经用了 `localStorage` + 心跳来跨浏览器标签页互斥。

若后台内部也允许多开同一篇文章，就必须区分「内部标签」与「浏览器标签」，
否则会出现自己锁自己。这套锁的复杂度会上一个台阶。

**3. 草稿存储按 slug 单键**

`DRAFT_KEY` 按文章 slug 区分。同一篇文章开两个标签时，
两个实例会争抢同一个 localStorage 键，后写的覆盖先写的 —— 数据丢失风险。

### 收益评估

标签页的价值在于「频繁在多个对象间来回切换且各自保有状态」。
但看实际使用场景：

| 场景 | 是否需要标签页 |
| :--- | :--- |
| 写文章时查配置 | 需要，但「预览」「目录」抽屉已能覆盖 |
| 同时编辑两篇文章 | 罕见；且草稿机制会冲突 |
| 在文章列表与编辑器间来回 | 需要，但浏览器后退已能实现 |
| 对照两个环境变量页 | 无此需求（只有一个环境变量页） |

**核心判断：本后台的主要工作流是线性的（列表 → 编辑 → 保存 → 回列表），
不是并行多任务的。** 标签页解决的是并行问题，而这里没有并行问题。

### 代价

| 项 | 代价 |
| :--- | :--- |
| 改造 `AdminDashboard` 的渲染模型 | 大（5663 行单实例 → 多实例容器） |
| 路由锁重构 | 中（区分内部/外部标签） |
| 草稿存储改为多实例安全 | 中（键需加实例 id） |
| 内存占用 | 每个编辑器实例持有完整 DOM 与状态 |
| 与现有 `applyRoute` / 页面动画的交互 | 需重新设计 |

## 四、替代方案（成本低得多）

| 方案 | 说明 | 成本 |
| :--- | :--- | :--- |
| **A. 保持现状 + 增强后退** | 已有 History API 真实路径，浏览器后退/前进可用。只需确认后退时草稿不丢。 | 极小 |
| **B. 编辑器内抽屉（已实现）** | 「文章信息」「目录」「历史版本」已是右侧抽屉，切换不离开编辑器。 | 0 |
| **C. 快速切换器** | `Cmd/Ctrl+K` 打开命令面板，输入标题跳转到任意页面。解决了「找页面慢」，不引入多实例。 | 小 |
| **D. 分屏对照** | 若确实需要同时看两样东西，用 CSS Grid 分两栏，比标签页简单。 | 中 |

## 五、结论

**不建议实现标签页体系。** 理由：

1. 收益与代价严重不匹配：需要重写渲染模型、路由锁、草稿存储，
   而它解决的问题（并行多任务）在本后台的工作流里不成立。
2. 存在真实的数据风险：同一篇文章多开会导致草稿互相覆盖。
3. 已有替代方案能覆盖 80% 的实际痛点（抽屉、后退、真实路径）。

**如果确实痛点是「找页面慢」**，建议做方案 C（命令面板），成本约 1/10，
且不触碰任何现有状态管理。

**如果痛点是「编辑时要参照别的内容」**，建议做方案 D（分屏），
比标签页更符合「同时看两样东西」的实际需求。

需要你确认：实际想解决的问题是「找页面慢」，还是「同时看两样东西」？
