# 模块 E 方案评估

> 依据 AGENTS.md「先给方案再写代码」：本文只评估，不改业务代码。
> 三项按代价从低到高排列：E3 → E1 → E2。

---

## E1 环境变量页：加侧边栏 + 模块化拆分

### 现状

`SecretManager.svelte` **1417 行**，已有分组机制但不是侧边栏：

```
SECRET_GROUPS = [github, auth, turnstile]   ← 3 个分组，定义在 utils/admin-secrets.ts
```

页面把 3 个分组**纵向堆在一页**，靠滚动浏览。所有密钥项（`SECRET_ROWS`）
也在这个文件里渲染、校验、保存。

### 问题

1. **1417 行单文件**：分组渲染、字段校验、环境探针、保存逻辑、导出 .env 全在一处。
2. **纵向堆叠**：3 组还好，但「便于接 KV」意味着分组会增加；
   每加一组，页面就长一截，用户要滚着找。
3. **无地址**：当前所有分组共用一个 URL（`/admin/env/`），
   没法直接跳到「就看 Turnstile 那组」。

### 建议方案

**两步走，互相独立，可分批交付。**

#### 第一步：加侧边栏（小改，纯 UI）

- 左列列出 `SECRET_GROUPS`（复用现有定义，不新增数据源）
- 右侧只渲染选中分组
- URL 加 segment：`/admin/env/github/`、`/admin/env/auth/`
  （与现有 `settings/:section` 的做法一致，`parseRoute` 已有先例）

**改动面**：`SecretManager.svelte` 模板与 `parseRoute` / `applyRoute`。
**风险**：低。分组数据已存在，只是换个呈现方式。

#### 第二步：模块化拆分（中改）

按职责拆成 3 个文件：

| 文件 | 职责 | 预计行数 |
| :--- | :--- | :--- |
| `SecretManager.svelte` | 容器：侧边栏 + 选中态 + 保存编排 | ~300 |
| `secrets/SecretFields.svelte` | 已存在，字段渲染 | 519（不变） |
| `secrets/SecretProbe.svelte` | 环境探针与状态判定（`verdictOf` / `groupOptional`） | ~250 |
| `utils/secret-draft.ts` | 已存在，草稿与序列化 | 不变 |

**收益**：容器只剩编排；探针逻辑可单独测试（当前 `verdictOf` 有 4 个分支，
埋在组件里无法单测）。

**风险**：中。要保证拆分后保存行为完全不变 —— 用现有测试覆盖。

### 与「接 KV」的关系

需求提到「便于接 KV」。查现状：`src/utils/secret-io.ts` **直接读写 `.env` 文件**
（`isEnvFileWritable()` / `applyEnvFileUpdates()` / `readSecretStates()`），
**没有 provider 抽象** —— 这一点与文章存储不同（文章走 `getStorageProvider()`）。

所以「接 KV」实际要动的是**存储层**：

1. 把 `secret-io.ts` 的读写抽成 provider 接口（本地 .env / KV 两个实现）；
2. 现有调用点（`SecretManager`、`/api/admin/secrets/`、`ensureManagedSecret` 等）改为经接口调用。

**E1 的侧边栏与这件事正交**：它只改变呈现，不碰存储。
但它有间接帮助 —— 侧边栏把「每组密钥」变成独立单元后，
按组决定「这组存本地还是存 KV」在 UI 上才有落点（当前纵向长页里无法表达这种区分）。

**结论**：E1 不推进也不阻碍 KV 接入；若要接 KV，那是独立的一项，应单独立项评估。

### 结论

**建议做第一步（侧边栏），第二步视情况。** 第一步风险低、收益立即可见；
第二步是代码质量改善，可以在做 E1 时顺带，也可以等它真的再长。

## E2 设置页分流：「管理类」页面移到侧栏

### 现状

设置页有 **24 个配置项**（`CONFIG_ITEMS`），全部在 `/admin/settings/` 下：

```
site / profile / navbar / footer / footer-html / music / friends / comment /
font / wallpaper / announcement / analytics / gallery / app / sponsor / license /
cover-image / effects / plantuml / code-theme / pio-spine / pio-live2d / sidebar / admin
```

而侧栏目前只有 7 个一级导航项：
`首页 / 文章管理 / 分类与标签管理 / 网站配置 / 环境变量 / 友链管理 / 会话管理`

### 问题

**同一类东西分散在两个地方**，且边界模糊：

- 「友链管理」在一级侧栏，但「友链配置」也在设置页（`friends` 项）—— 两处都能改友链。
- 「分类与标签管理」在一级侧栏，但它是内容管理，与「文章管理」同级。
- 设置页里既有**纯配置**（字体、主题色、代码高亮），也有**数据量很大的配置**
  （相册 `gallery`、软件推荐 `app`、公告 `announcement`）—— 后者虽然是配置文件，
  但编辑体验更接近「管理一堆条目」，和改一个开关放同一列里不协调。

用户不知道「想改 X 该去侧栏还是设置页」。

### 建议方案

#### 按「改的是什么」分类，不按「代码里在哪」

| 类别 | 内容 | 去处 |
| :--- | :--- | :--- |
| **内容** | 文章、分类、标签、友链条目 | 一级侧栏（内容管理组） |
| **展示内容** | 相册、软件推荐、公告（均为配置文件，但内容量大） | 设置页内独立分组 |
| **外观** | 字体、壁纸、主题色、代码主题、特效、看板娘 | 设置页（外观分组） |
| **行为** | 导航栏、页脚、评论、统计、PlantUML、后台外观 | 设置页（行为分组） |
| **集成** | 环境变量、GitHub 同步、会话 | 一级侧栏（系统组） |

具体调整建议：

1. **「友链管理」与设置的 `friends` 项合并**，只留一处。
   现状是侧栏管条目的增删改，设置页管开关与样式 —— 应在同一页分两个标签。
2. **`gallery` / `app` / `announcement` 在设置页内独立成组**。
   注意：它们**都是配置文件**（`galleryConfig.ts` / `appConfig.ts` /
   `announcementConfig.ts`），不是内容文件 —— 所以**不应该迁到一级侧栏**，
   而是在设置页里与「字体/壁纸」这类纯外观项分开，避免混在一列。
3. 设置页**加侧边栏二级导航**（和 E1 同样的交互），把 24 项分成 3 组。

#### 可选：混合页面方案

即「一个页面内既有配置表单，也有条目列表」。这在友链上已经事实上存在
（侧栏管理条目 + 设置页配开关）。建议**显式做成两段**：
上半是配置，下半是条目列表，而不是分散在两个路由。

### 代价与风险

| | 说明 |
| :--- | :--- |
| 改动面 | 大：涉及侧栏导航结构、设置页路由、至少 3 个页面的归属调整 |
| 风险 | 中高：URL 变化会让用户书签失效，需要重定向（现有 `applyRoute` 已有归一化先例，如 `/admin/user/` → `/admin/env/`） |
| 收益 | 中：消除「两处都能改友链」的困惑，侧栏与设置页职责清晰 |

### 结论

**建议做，但需要拆成可独立交付的小步**：

1. **先做归类**（不改代码）：确定 24 项各自属于内容/外观/行为/集成，写进文档。
2. **再做设置页二级侧栏**（与 E1 同一套交互，可复用）。
3. **最后处理友链合并与内容类迁出** —— 这一步会改 URL，需要重定向。

不建议一次全做：URL 变动 + 导航重构 + 页面归属三者同时改，
出问题时很难定位是哪一处。

## E3 导出：单文件 JSON → 含资源的 Zip 包

### 现状

`exportPosts()`（`AdminDashboard.svelte:725`）流程：

```js
for (const p of posts) {
  const res = await fetch(`/api/admin/post-content/?slug=${p.slug}`);
  bundle.push({ slug, filePath, content, ...frontmatter });
}
// 输出 { version: 1, exportedAt, posts: [...] } 的 .json
```

**导出内容**：仅文章的 Markdown/MDX 正文 + frontmatter。
**不含**：文章引用的图片、附件。

### 问题：具体在哪里

1. **导出的 JSON 不完整**。文章里写了 `![](images/foo.avif)`，
   导入到另一台机器后图片全断 —— 因为图片没进包。
2. **需要逐个 slug 请求**。24 篇文章就是 24 次串行 fetch，
   导出体验随文章数线性变差。
3. **无法作为备份**。用户以为导出的是「全部内容」，
   实际上裸 JSON 恢复不了站点。

### 技术可行性

**依赖**：项目已有 `pako ^2.1.0`（deflate）。zip 格式可以基于它手工生成
（store/deflate + 中央目录），无需新增依赖。若嫌手工繁琐，可选 `fflate`
（~10KB，比 jszip 小一个数量级），但按「不新增依赖」原则，
**优先用现有 pako**。

**资源规模实测**：

```
src/content/posts/ 下图片：15 个，合计 1.14 MB
```

规模很小，完全可以在浏览器端组装。

### 建议方案

#### 方案 A：Zip，浏览器端组装（推荐）

1. 新增 `/api/admin/export-bundle/` 返回所有文章正文（**一次请求**，替代 24 次）
2. 前端收集文章引用到的资源路径，逐个从 `/api/admin/post-asset/` 拉取
   （该接口已存在，且已限制在 `src/content/` 与 `public/` 内）
3. 用 pako 生成 zip：`posts/*.md` + `assets/*` + `manifest.json`
4. `manifest.json` 记录版本的资源映射，供导入时还原路径

**优点**：一个文件包含完整内容，可直接当备份；导入能真正恢复站点。
**风险**：导入侧要处理路径重写；需定义 manifest 格式并保持向后兼容。

#### 方案 B：改进现有 JSON（小改）

只把图片转成 base64 内联进 JSON。

**优点**：改动最小，无 zip 实现。
**缺点**：base64 体积膨胀约 33%；JSON 解压不可读；
图片多时文件巨大且编辑器打不开。

#### 方案 C：不改（保持现状 + 明确文案）

**优点**：零成本。
**缺点**：导出仍然不可用于备份，用户会继续误解。

### 结论

**建议做方案 A**，但**分两步**：

1. **先做「一次请求」的聚合**（`/api/admin/export-bundle/`）——
   这是纯性能改善，不改文件格式，可独立交付。
2. **再加 zip 打包与 manifest** —— 这一步引入新格式，需要同时做导入侧。

**必须同时定义 `manifest.json` 并写进文档**，否则「导入」无法还原路径。
若只做导出不做导入，那就不是备份功能，价值要打折。

## 三项优先级建议

| 项 | 代价 | 风险 | 建议 |
| :--- | :--- | :--- | :--- |
| **E1 第一步**（环境变量侧边栏） | 小 | 低 | **先做** —— 复用现有 `SECRET_GROUPS`，纯 UI |
| **E3 第一步**（聚合请求） | 小 | 低 | **次做** —— 纯性能，格式不变 |
| **E1 第二步**（模块化拆分） | 中 | 中 | 可顺带或延后 |
| **E3 第二步**（zip + manifest） | 中 | 中 | 需同时做导入，否则价值打折 |
| **E2**（设置页分流） | 大 | 中高 | **最后做，且必须拆小步** —— 会改 URL |

## 需要你确认

1. **E1**：只做第一步（侧边栏），还是连模块化拆分一起？
2. **E2**：是否接受 URL 变动（旧书签会失效，我会加重定向）？
3. **E3**：只做导出，还是导出 + 导入（真正可恢复的备份）？
