# 后台安全管理计划 · 2026-10-13

来源：对 `docs/todo/单管理员博客：初始化、会话与凭据安全设计.md` 的多轮评估讨论。

**评估结论**：该文档约七成目标本项目已实现，且会话部分比文档更完整（文档设想"服务端不追踪会话"，本项目的会话表更强）。真正要新增的只有两块：**登录层 IP 封禁（应急缓冲）** 与 **平台层核按钮（写成运维手册）**。文档中假设的 Cloudflare Workers / `wrangler` / `admin.json` 与本项目现实不符，全部不采纳。

---

## 0. 威胁模型边界（讨论确定）

- **范围内**：应用层凭据或会话失守。
  - 撞库成功（攻击者拿到密码）；
  - 会话 cookie 被窃（攻击者拿到有效会话）。
- **范围外**：**Vercel 平台账号**失守。攻击者能改平台 env、删部署、读全部 secret，项目代码无力阻止，不做任何处理。
- **推论 1**：项目侧不承担"对抗已入侵者"，只做"**争取时间的缓冲** + 日常运维"。
- **推论 2**：真正的核按钮必须落在**攻击者够不着的地方**（平台 env / Vercel Firewall）。
- **推论 3**：任何**只存在 `persist-store`（KV）** 的控制手段，在"攻击者同时掌握 `KV_REST_API_TOKEN`"的假设下不可靠——他能解封自己、恢复/伪造会话。**该条为下方开放问题 Q1 的前提。**

## 2. 现状缺口（本次要处理的）

| # | 缺口 | 落点 | 风险 / 动机 |
|---|---|---|---|
| **G1** | 登录层**没有 IP 黑名单**，只有自动锁定（自过期、不可点名、不可持久） | `login-guard.ts` + `verify.ts` | 无法主动、长期地挡已知攻击来源 |
| **G2** | 无法**按 IP 踢会话**（只能按 `sid`） | `session-store.ts` | 封 IP 只挡新登录，挡不住攻击者**已有**的会话 |
| **G3** | `DELETE /api/admin/sessions` **无二次验证** | `sessions.ts:60-67` | 攻击者持会话即可 `?allOther=1`（`:80`）把真管理员全部踢掉 |
| **G4** | 非认证破坏性密钥（如 `GITHUB_PRIVATE_KEY`）改写入**无二次验证** | `secrets.ts:35-39`、`:122-139` | 会话被盗 ≈ 仓库写权限被盗（无需任何密码即可覆盖私钥） |
| **G5** | **无终端核按钮**（全踢 / 封 IP 的带外包装） | `scripts/` + 运维手册 | 危急时刻 Web 进不去，没有自救入口 |

## 3. 计划

### P0 · 登录层 IP 封禁（本次核心，阻塞于 Q1/Q2）

**动作 = 加入黑名单（挡新登录） ＋ 踢掉该 IP 的现有会话（挡当前会话）**——两者必须一起做，才实现"他有密码也没办法"。

- `src/utils/login-guard.ts`：新增 `isIpBanned(ip)` / `banIp(ip, opts)` / `unbanIp(ip)` / `listBanned()`，复用既有 `getClientIp`、`getStore`、`writeAuditLog`；新增审计事件 `ip_banned` / `ip_unbanned`（`login-guard.ts:290-301` 联合类型）。
- `src/utils/session-store.ts`：新增 `revokeSessionsByIp(ip)`，复用 `listSessions` 已有的 `ip` 字段（`session-store.ts:28`）；复用 `verifyDeleted` 处理删除竞态。
- `src/pages/api/admin/verify.ts`：在 `clientKey`（`:46`）之后、闸门（`:88`）之前加黑名单拦截，返回 403（与锁定用 429 区分）。
- 封禁入口：会话管理页对某 IP 一键封（Web）+ CLI 兜底。
- 测试：`tests/login-guard.test.ts` 补黑名单用例、`tests/session-store.test.ts` 补 `revokeSessionsByIp`；**必须做变异测试**确认断言有效。

### P1 · 平台层核按钮（写成运维手册，非代码）

在 Vercel 上没有服务器终端，应急动作全部落在平台层：

| 动作 | 操作 | 效果 |
|---|---|---|
| 轮换 `ADMIN_JWT_SECRET` | 平台 env 改值 + redeploy | 全部旧 JWT 立即失效（即使 KV 被篡改也没用，验签失败） |
| 重设 `ADMIN_PASSWORD` | 平台 env 改值 + redeploy | 攻击者掌握的密码作废 |
| 封 IP | **Vercel Firewall**（付费计划） | 不占应用 KV，攻击者解不了 |

可选：本机 CLI（如 `scripts/admin-*.ts`，用项目已有的 `tsx` 跑）把上述三步 + `admin:revoke-all` / `admin:unban` 包装成命令；线上操作需先 `vercel env pull` 拿 KV 凭据。

### P2 · 顺手加固（可与 P0 合并或后置）

- 给 `sessions.ts` DELETE（至少 `allOther` 分支）加二次验证，堵 G3。
- 把 `AUTH_KEYS`（`secrets.ts:35-39`）的二次验证扩展到 `GITHUB_PRIVATE_KEY` 等破坏性密钥，堵 G4。
- 登录成功加**带外告警**（邮件/Webhook），攻击者一登录即知。

### 明确不做

- 迁移 Cloudflare Workers（`CLAUDE.md` 已实测否决：scrypt 峰值 189MiB > 128MB、CPU 484ms、无 KV adapter）。
- 引入 `admin.json`（现状 `.env.local` + 平台 env 已满足，且被测试锁住）。
- 拆掉 Web 的会话/密钥管理页（现状能力更强，终端只作带外兜底）。
- 把"对抗已入侵者"塞进应用内 KV（见推论 3）。

## 4. 开放问题（阻塞 P0 实现）

- **Q1**：攻击者是否可能掌握 `KV_REST_API_TOKEN`？
  - 若否（仅撞库拿到密码）→ 黑名单存 KV 可靠，P0 按上述实现。
  - 若是 → 黑名单必须放**平台层**（Vercel Firewall），应用内只做"按 IP 踢会话"。
- **Q2**：误封自己（同一 NAT / 动态 IP）后的**解除通道**形式？
  - 建议：本地 CLI `admin:unban <ip>`，或直接在平台层解除。
